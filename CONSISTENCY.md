# Product Data Consistency Contract

## The Problem This Solves

In e-commerce ML systems, a common bug is **product ID drift** — the frontend,
backend, and ML pipeline use different products for the same ID. This means:

- Click events logged with frontend product ID 5 don't join to the backend's
  product ID 5 if they refer to different items
- ML models trained on one catalogue can't serve meaningful recommendations
  for a different one
- A/B test and evaluation metrics are meaningless because the models being
  compared were never evaluated against what's actually being served

## Our Contract

**Single source of truth: `backend/data/processed/products.json`**

That file is generated by `backend/generate_large_catalog.py` — 5,060
products across 11 categories, each mapped to a real per-item-name Zepto CDN
image where one exists, with a normal-distribution price/rating spread.
Three things are derived from it, and only it:

| Consumer | How it gets the catalogue |
|----------|---------------------------|
| Live database (Supabase Postgres) | `backend/seed_db.py` reads `products.json` and inserts it as-is — same ids, same fields |
| ML pipeline (`ml_research/`) | `02_collaborative_filtering.py` loads `products.json` directly; all downstream artifacts (FAISS index, CF factors, hybrid ranker) are trained against these exact ids |
| Frontend (`frontend/src/lib/products.ts`) | Also written by `generate_large_catalog.py` in the same run — same ids, same fields, just re-shaped to the frontend's `Product` type |

Because all three come from one generation run, a product ID means the same
product everywhere: an event logged against product 4213 from the frontend,
a FAISS neighbour returned for product 4213, and the `products` row with id
4213 in Postgres are all the same item.

## Why product IDs start at 0

`generate_large_catalog.py` assigns ids sequentially starting at 0, matching
array/list conventions in both the Python ML pipeline and the TypeScript
frontend — no translation layer needed anywhere.

## What happens if you regenerate the catalogue?

Regenerating changes every downstream artifact's idea of "what product 4213
is," so all three consumers need to move together:

1. Run `python backend/generate_large_catalog.py` — rewrites
   `backend/data/processed/products.json` and `frontend/src/lib/products.ts`
2. Re-seed the database: `python backend/seed_db.py`
3. Retrain the ML pipeline so its artifacts match the new ids:
   `python ml_research/02_collaborative_filtering.py` →
   `03_content_embeddings.py` → `04_hybrid_ranker.py`

Skipping step 2 or 3 after a regeneration is exactly the drift this contract
exists to prevent — the frontend would show new products, but recommendations
and similar-product lookups would still be reasoning about the old ones.

## Verification

```bash
python backend/verify_products.py
```

Checks that the database, `products.json`, and `frontend/src/lib/products.ts`
all agree on product count and spot-checks a sample of ids for matching
name/price across all three.
